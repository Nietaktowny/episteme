# The event log

Besides the *state* of the vault (the `notes` table and the views on it), Episteme keeps a *history*: an
append-only table, `events`, that records what happened, when, and to what. It is the base of every question that
starts with "how often", "since when" or "how long": how many evergreen notes a week, how long a violation stays
open, whether the last sync ran.

It is built in layers, a small simulation of a medallion architecture, so that the data can evolve:

| Layer | What | Where |
|---|---|---|
| Bronze | Loose facts: a few fixed columns and a JSON `payload`. Never updated. | the `events` table |
| Silver | The same facts with the interesting payload fields promoted to columns. | views (per event type) |
| Gold | Answers: open alerts, time to fix, activity per day. | views and the star schema |

A field starts life inside the payload. When it is queried often, a view promotes it to a column; when it is
queried by everything, a migration makes it a column of `events` (as `type` and `created` became columns of `notes`).

!!! note "What is built"
    The bronze table, the dimensions, the events a sync records (notes, tasks and sync runs), the events for what Episteme itself
    does, the silver and gold views, the health lifecycle for every rule of the catalog but two (S4 and T2, which are in the
    catalog with `is_active` false: see [Health rules](#health-rules)), and the delivery of alerts to sinks. The rule catalog below is complete already, with `is_active` telling which rules
    something evaluates.

## The `events` table

| Column | Meaning |
|---|---|
| `event_id` | UUIDv7, generated by Episteme; ids sort by time of creation. |
| `system` | Which system the event is about: `obsidian`, `anki` or `episteme`. A `sync.completed` event has the system that was synced. |
| `category` | `state` (something changed), `health` (a rule found or stopped finding a problem) or `system` (Episteme's own operation: a sync, a check). |
| `event_type` | `<entity>.<verb>`, e.g. `note.created`. See `dim_event_type`. |
| `event_version` | The version of the payload's shape; for a health event, the version of its rule. |
| `rule_id` | The rule, for health events (`R9`). |
| `entity_id` | What it is about: a note path, a task id. `NULL` for an event about a run. |
| `occurred_at` | When it happened, as far as is known: a frontmatter date, a file time or the time the sync noticed. UTC. |
| `inserted_at` | When the row was written to the database. UTC. Set by the database; compare with `occurred_at` to debug. |
| `occurred_date` | The day of `occurred_at` (UTC); computed by the database, indexed. |
| `run_id` | Groups the events of one sync or check. |
| `producer` | The Episteme version that wrote the row. |
| `dedupe_key` | Unique: recording an event twice stores it once. |
| `deleted_at`, `is_deleted` | Soft delete. Set `deleted_at`; `is_deleted` is computed from it, so the two can never disagree. |
| `payload` | JSON with the rest. Metadata and counts, never the content of a note. |

The table is the same on DuckDB and SQL Server and uses no feature that only one of them has (no triggers,
sequences or identity columns): ids and keys are made by Episteme. DuckDB cannot run triggers at all, which is
why the soft-delete flag is computed instead of maintained.

Events are never updated. To remove one, soft-delete it (`Database.delete_events`); the views leave deleted events
out, and the `dedupe_key` stays taken, so a producer that records the event again does not bring it back.

```python
for event in episteme.data.iter_events(event_type="note.updated", entity_id="30_Resources/Evergreen/AI/Attention.md"):
    print(event.occurred_at, event.payload["properties"])
```

## What a sync can and cannot tell

A sync sees a state, not a change; the events are inferred by comparing it with the previous state. They are
therefore only as fine as the sync interval: three edits between two syncs are one `note.updated`, and the
event's `occurred_at` is the file's modification time or the moment the sync noticed. Hence:

- **`note.discovered`.** The first sync that records events records every note as discovered, not as created: a
  note that was there when the log started was not created while the log was watching.
- **`note.created`.** `occurred_at` is the note's frontmatter `created` day when it has one (`payload.occurred_basis` says
  so), else the time the sync saw it.
- **`note.updated`.** Only when the frontmatter, the body or the type changed. Touching a file does not count.
  The payload lists what changed (`changed`, `changed_keys`) and the old and new values of a few tracked
  properties (`type`, `status`, `domain`, `lane`, `parent`, `kind`, `ankified_date`, `closed_date`,
  `review_cycle`, `last_review`).
- **`note.moved`.** A path vanished and another appeared with an identical non-empty body (renamed, moved, archived).
  An ambiguous or empty match is a delete plus a create.
- **Task events** (`task.discovered`, `created`, `updated`, `completed`, `deleted`) follow the same rules, for the tasks that have
  an id. A move of the line, or an edit of the text, is not an event; a change of state, a date, the priority or the note is.
  The payload has the note, the state, the due date and the priority: never what the task says.
  A task that appears already done is *created*, not completed: it was not seen being done.
- **`sync.completed`** is recorded in the same transaction as the notes it describes, so the log never disagrees with them.
  **`sync.failed`** cannot be: the failed transaction rolls back, so it is written on its own afterwards.

`episteme data clear` removes the notes and their tasks, not the log.

## What Episteme did, and what a sync saw

A sync records what *happened to the vault*. Episteme also does things itself, and those are events of their own, `action.*`:
`action.note_created` (a note made from a template), `action.task_added`, `action.task_updated`, `action.task_completed`,
`action.task_deleted`, `action.snapshot_taken` and `action.data_cleared`. They are recorded when the action has worked, by the
method that does it (`Episteme.new_note`, `add_task`, `edit_task`, `delete_task`, `Database.snapshot`, `Database.clear`), whichever way it
was called: the command line, the TUI or code. A log that cannot be written does not undo the action; the failure is only logged.

A note made by Episteme is an `action.note_created` now and a `note.created` at the next sync. They are not duplicates: the first says
**who did it**, the second says **what the vault shows**, and a note made in Obsidian has only the second. Like the other events, they
carry the note's path, the template, the type and the state, never what a note or a task says.

`episteme db clear` removes the notes, tasks and Anki statistics, not the log; it records `action.data_cleared` with how much it removed.

## Dimensions

The dimension tables describe what the log says, for joins in a BI tool. The first two are copies of catalogs in the
code (`episteme.models.events`) and are refreshed whenever a database opens.

| Table | Rows |
|---|---|
| `dim_event_type` | One per kind of event: system, category, current version, description. |
| `dim_rule` | One per **version** of a health rule: id, name, group, kind, severity, description, remediation, parameters, `valid_from`, `valid_to`. |
| `dim_severity` | `info`, `warn`, `error` with a rank. |
| `dim_date` | The calendar 2000–2049: year, quarter, month, ISO year and week, weekday, `is_weekend`. English names whatever the locale. |

### Versions

A rule gets a new `dim_rule` row, and the old one is closed (`valid_to`), when its logic changes (`logic_version`, bumped in
the code) or its effective parameters change (a different `params_hash`, e.g. a configured threshold of 30 days instead of 14).
A health event is written with `event_version` equal to the rule's `rule_version` at that moment, so an old violation
always joins to the rule as it was. `rule_sk` is the single-column key for tools that cannot join on two columns.

## Views

Every view leaves out soft-deleted events.

| View | Layer | Contents |
|---|---|---|
| `note_events` | silver | One row per note event, with the payload's fields as columns: `note_type`, `moved_from`, `size_delta`, `changed`, `changed_keys`, `type_before`/`type_after`, `status_before`/`status_after`, `is_baseline` (a `note.discovered`). |
| `fact_events` | gold | One row per event, the transaction fact. Keys: `occurred_date` → `dim_date`, `event_type` → `dim_event_type`, `rule_sk` → `dim_rule` (the rule version in force when the event was written), `severity` → `dim_severity`, `entity_id` → `dim_note`. |
| `fact_sync_runs` | gold | One row per sync of a system, succeeded (`ok`) or failed (`error`, `message`), with its counts and durations. |
| `activity_daily` | gold | Per day: notes created, updated, moved and deleted, how many different notes that touched, and tasks created and completed. The baseline is not counted. |
| `dim_note` | gold | The notes as they are now. A note that is gone has events but no row. |
| `health_findings` | detector | Every violation found right now: `(rule_id, entity_id, detail, severity)`. The contract of a detector: `property_issues` (R1–R19) and `health_detections` (the other rules) joined to `dim_rule`. |
| `health_detections` | detector | The violations of the structure, knowledge, cadence, task, system and event rules, one row each. |
| `rule_limits` | detector | The limits of every rule in force (`days`, `hours`, `max_count`, `max_percent`, `error_after_days`), from `dim_rule.parameters`. |
| `action_events` | silver | What Episteme itself did (`note_created`, `task_added`, `task_updated`, `task_completed`, `task_deleted`, `snapshot_taken`, `data_cleared`) with `note_path`, `state`, `template`, `note_type`, `notes` as columns. |
| `alert_deliveries` | silver | Every alert sent to a sink (`ok`) and every attempt that failed (`error`): `violation_id`, `sink`, `kind`, `severity`, `rule_id`. |
| `task_events` | silver | The task events with `note_path`, `state`, `previous_state`, `due_date`, `priority` as columns. |
| `health_events` | silver | The health events with `detail`, `in_archive`, `note_type`, `reason`, `is_baseline` as columns. |
| `fact_violations` | gold | One row per violation **episode**: `opened_at`, `resolved_at`, `resolution`, `days_open`, `reopen_count`. Keys: `rule_sk`, `severity`, `opened_date`, `entity_id`. |
| `open_alerts` | gold | The open episodes of the active vault (not the archive), with severity, `days_open`, and what the rule says (`description`, `remediation`). |

```sql
-- How the vault moves, week by week
SELECT d.iso_year, d.iso_week, sum(a.notes_created) AS created, sum(a.notes_updated) AS updated
FROM activity_daily a JOIN dim_date d ON d.date_key = a.occurred_date
GROUP BY d.iso_year, d.iso_week ORDER BY 1, 2;

-- Has the last sync of each system worked?
SELECT system, max(finished_at) AS last_ok FROM fact_sync_runs WHERE ok GROUP BY system;
```

## Health: from violations to alerts

A *detector* says what is wrong **now**; the log remembers **since when**. After every sync Episteme runs a health check
(`Episteme.check_health`, or `episteme health check`):

1. It reads `health_findings`, the union of the detectors. The registry rules R1–R19 come from the `property_issues` view;
   a new detector is any view with the same columns added to the union.
2. It compares them with the open episodes of `fact_violations`. A finding that is not open becomes
   `health.violation_opened`; an open violation that is not found any more becomes `health.violation_resolved`, with
   `reason` `fixed`, `note_gone` when its note is no longer stored, or `rule_removed` when its rule has left the catalog (the open
   violations of a removed rule are closed at the next check, so they do not stay open for ever).
3. It records `health.check_completed`, so that a clean vault can be told from a check that never ran.

All of it in one transaction. A violation is identified by `(rule_id, entity_id, detail)`: a note with two deprecated
properties has two violations, and fixing one resolves one. A violation that comes back is a new episode
(`reopen_count` + 1), which is what makes flapping visible.

!!! warning "The first check is a baseline"
    The first check of a database finds every violation at once, and they are marked `is_baseline`: they are older than the
    log, so their `opened_at` is when they were first seen, and `days_open` is a lower bound. Leave baseline
    episodes out when measuring how long violations take to fix.

Violations in the archive (`40_Archive/`) are recorded (`in_archive`) but are not alerts: the registry does not require
rewriting archived notes.

```bash
episteme health                    # the open alerts, most severe first
episteme health --severity warn    # warnings and errors
episteme health --rule R9          # one rule
episteme health --fail-on error    # exit 1 if there is an error: for scripts
episteme health check              # run the check now
episteme health rules              # the catalog
episteme doctor                    # includes the number of open alerts
```

The same alerts are in the TUI (the *Health* tab) and in the `open_alerts` view for BI tools.

```sql
-- How long do violations take to fix, per rule? (Baseline episodes are left out.)
SELECT rule_id, count(*) AS fixed, avg(days_open) AS avg_days
FROM fact_violations WHERE resolved_at IS NOT NULL AND NOT is_baseline AND resolution = 'fixed'
GROUP BY rule_id ORDER BY avg_days DESC;
```

## Sending alerts

Alerts are in `episteme health`, the TUI, `doctor` and `open_alerts`. To have them *come to you*, configure **sinks**. A sink is a command
or a webhook that receives each alert as JSON (everything in `open_alerts`: the rule, the note, the severity, what to do):

```bash
ALERTS__SINKS='[
  {"name": "phone",   "kind": "webhook", "url": "https://example.com/hook", "headers": {"Authorization": "Bearer ..."}, "min_severity": "error"},
  {"name": "desktop", "kind": "command", "command": ["/home/me/bin/episteme-notify"], "min_severity": "warn"}
]'
```

- A **command** is run without a shell, with the alert on its standard input, so anything that reads standard input will do: a script that calls
  `notify-send`, posts to a chat, appends to a file. A non-zero exit is a failed delivery.
- A **webhook** is POSTed the alert as JSON; an answer other than 2xx is a failed delivery. Use `https`: the alert names notes.
- `min_severity` (default `error`) is per sink. `ALERTS__LIMIT` (default 20) is the most one sink gets per check, so a messy vault
  is not a flood; the rest wait for the next check. `timeout` (default 10 s) is per sink.

Which alerts a sink still has to get is decided by the log, not by the sink: every delivery is an `alert.delivered` event, and an alert is
sent to a sink **once per severity**. When it is escalated (E1) or its detector makes it worse, it is sent again. A failed delivery is an
`alert.delivery_failed` event and is tried again at the next check; it never fails the sync or the check.

Left out on purpose: the alerts of the archive, and the alerts of the **first check of a database** (the baseline: they are as old as the vault, not
news; `ALERTS__INCLUDE_BASELINE=true` sends them). The settings are checked when they are read: a sink needs its command or an http(s) url, and
names are unique.

```bash
episteme health notify --dry-run   # how many alerts would be sent
episteme health notify             # send them now (a sync or a scheduled health check does it too)
```

```sql
SELECT sink, severity, count(*) FILTER (WHERE ok) AS sent, count(*) FILTER (WHERE NOT ok) AS failed
FROM alert_deliveries GROUP BY sink, severity;
```

The alert contains the path of a note and what is wrong with it. Treat a sink as you would the vault: a webhook is a place your note
names are sent to.

## Health rules

Every rule has an id, a name, a severity, a description and a remediation, in `dim_rule`:

| Group | Ids | What |
|---|---|---|
| registry | R1–R19 | The violations the `property_issues` view finds. |
| structure | S2–S5 | Duplicate content, untyped notes, type and folder disagreeing, stray empty notes. (S1, duplicate note names, was removed.) |
| knowledge | K1–K4 | Evergreens never or stale in Anki, aging placeholders, a gap in Anki reviews. |
| cadence | D1–D6 | Overdue reviews, weekly review gaps, missing daily notes, aging meeting inbox, stale or long-paused projects. |
| tasks | T1–T2 | Overdue tasks, duplicate task ids. |
| system | Y1–Y4 | Failed or stale syncs, mass deletion, a health check that did not run. |
| events | E1–E5 | Questions asked of the log: escalation, spikes, flapping, mass change, drought. |

```sql
SELECT rule_id, name, severity, is_active, description FROM dim_rule WHERE valid_to IS NULL ORDER BY rule_sk;
```

Two rules are in the catalog but nothing evaluates them, and `is_active` says so. **S4** (`type_folder_mismatch`) needs the
folder-to-type mapping, which is a setting of the vault and not in the database. **T2** (`duplicate_task_id`) is only known to
the sync that sees the duplicates, because the database keeps just the first task of a duplicate.

What the other rules look at, where it is not obvious:

- **Ages** go by the dates a note carries (`created`) where it has them, and by the file's modification time where it
  does not (K2, K3, D5, D6). The modification time can move when files are copied between machines, so those rules can
  over- or under-report, like `evergreen_anki_state`.
- **A task** is identified by its id, with its note in the `detail`: moving it to another note closes one violation and
  opens another. Its severity is `error` once it is more than `error_after_days` days overdue, `warn` before.
- **System and event rules** (Y, E) are questions asked of the log. They are only answered when the check runs, so a
  scheduled check (`SCHEDULER__HEALTH_CRON`) is what makes `sync_stale` and `health_check_not_run` useful: a sync that does
  not run cannot notice itself. The baseline is not a spike, and the system's own alerts (Y, E) are not counted by E2 and E3.

### What the rules do not look at

Some notes are not meant to follow the registry, and checking them only made noise. `health_findings`, the input of the check, leaves
these out, so they are never opened as alerts:

| What | Not checked by | Why |
|---|---|---|
| Templates (`type: template`, or in `99_Templates/`) | R2, R6, R7, S2, S5 | They hold `{{placeholders}}`, and consecutive versions are near copies. |
| Notes in `_system/` | R1, R2, S3 | Tools write them, not you. |
| Notes in `00_Inbox/` | S3 | Unstructured capture needs no `type`. |
| Notes whose `template_version` is missing or below 1.1 | R2, R17 | They predate `created` (sources) and `start_range` / `end_range` (weekly reviews); history is not rewritten. |

The cutoff is the note's own `template_version`, so a new note that has none is not checked by R2 and R17 either: record the template
version when you create a note.

A property with an empty value is not an invalid one: R6 (dates) and R14 (`year`) treat a blank value and an empty list (`consumed_on: []`) alike
as no value. A tool that rewrites the frontmatter, such as the Obsidian MCP, writes the empty ones as `[]`.

### Limits

The threshold rules have limits in their `parameters` (`days`, `hours`, `count`, `percent`, `error_after_days`; see
`episteme health rules`). Change them in the settings, by rule id:

```bash
HEALTH__RULES='{"K1": {"days": 30}, "D5": {"days": 60}}'
```

A rule or a limit that does not exist is an error, not a silent no-op. A changed limit makes a **new version** of the rule
(see [Versions](#versions)): the detectors read the limits from `rule_limits`, so they follow at once, and the violations
found earlier keep the version they were found with.

### Severity

A violation has a severity. It starts as its detector says (`task_overdue` says `warn` or `error`; the others have their rule's) and
can change while the violation is open: the check records a `health.severity_changed` event when it does. Rule **E1**
(`violation_escalation`) raises a violation's severity one level once it has been open for `days` days (info → warn → error). It
is applied by the check itself and is not a violation of its own. It leaves the Anki backlog rules (K1, K2, K3) alone: a backlog
grows slowly, and escalating all of it would turn every waiting note into an error. `fact_violations.severity` and `open_alerts.severity` are the
latest of the episode.
